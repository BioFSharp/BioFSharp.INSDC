# BioFSharp.INSDC roadmap: persistent, curatable ArcIR

> **Status: ACTIVE (2026-08-20).** This is the single authoritative implementation plan for the repository. Historical plans are retained in place and classified in the [plan registry](#historical-plan-registry).

## Purpose

The repository already reads, writes, crawls, stores, and maps INSDC metadata into a useful proof-of-concept property graph. The next objective is to turn that proof of concept into a target-neutral intermediate representation that can be persisted and curated inside an ARC:

- **F1** ingests source metadata into one initial ArcIR state.
- **Curation activities** transform that state into later states while preserving fragment-level provenance.
- **F2** compiles a selected ArcIR state into target artifacts without changing the IR.
- The curation ARC's process graph records every activity and artifact revision.

The design of this system is itself an ARC. Source XML, SSSOM mapping sets, transformation records, diagnostic reports, the canonical ArcIR file, and generated target files are ordinary versioned artifacts connected through the ARC process graph.

```text
source artifacts + SSSOM --F1 once--> canonical ArcIR --curation*--> selected revision --F2*--> target artifacts
```

## Locked architectural decisions

1. **One canonical IR file.** A curation ARC contains one canonical `*.arcir.json` path. The working-tree path stays fixed while Git blobs and commits provide immutable revisions; curation edits that path rather than creating numbered snapshots.
2. **No `ArcDocument` domain envelope.** `ArcIR` is the in-memory graph. Its JSON root is only the persistence boundary `{ "formatVersion": "1.0", "graph": ... }`; process history and reports do not live in it.
3. **No embedded diagnostics.** F1, curation, and F2 use one `Diagnostic`/`DiagnosticReport` model. Reports are sibling artifacts generated by activities, so later validation cannot mutate an older IR state.
4. **No patch chain as authority.** Git diffs may be displayed and patches may be exported as derived conveniences, but replaying patches is never required to reconstruct a state.
5. **Fragment references are revision-bound.** A selector is meaningful only together with the path, digest, and optional Git commit of the artifact it selects.
6. **Stable identity for curatable units.** Objects, type assertions, properties, relations, and annotations that can be curated independently have persistent IDs and are serialized as keyed maps, not positional arrays.
7. **SSSOM contains reusable semantic mappings only.** Extraction paths, parsing, splitting, graph construction, and per-record execution history belong to transformation rules and records rather than mapping rows.
8. **F1 runs once per curation lineage.** Later corrections are explicit curation activities. A materially new source import starts an explicit new lineage; it does not silently replace curated work.
9. **F2 is repeatable and non-mutating.** It consumes an exact IR revision and generates target artifacts, a transformation record, and a diagnostic report. This roadmap defines the interface but no concrete F2 target.
10. **Breaking changes are accepted.** There is no compatibility facade for the proof-of-concept ArcIR API or its current HTML export.
11. **Local terms remain legitimate.** An unmapped INSDC term is preserved as a stable local term and diagnosed; absence of an external ontology match does not make the IR invalid.
12. **The first workbench is read-only.** Editing and committing curation actions through the UI belong to a later phase after the curation library and process model are stable.

## Phase 2 — Extract the target-neutral ArcIR core

Create a new packable `BioFSharp.ArcIR` project containing only the graph model, identity/value types, graph operations, validation, and persistence contracts. `BioFSharp.INSDC.ArcIR` becomes the INSDC-specific F1 adapter and depends on the core. The core must not reference generated INSDC types, INSDC vocabulary, crawler code, SQLite, or any target format.

### Public model changes

Introduce strongly typed `AssertionId`, `RelationId`, `AnnotationId`, and `DiagnosticId` values alongside `ArcId` and `Iri`.

- `ArcIR.Objects` remains `Map<ArcId, ArcObject>`.
- `ArcObject.Types` becomes an ID-keyed map of type assertions rather than an unaddressable set.
- `ArcObject.Properties` becomes `Map<AssertionId, ArcProperty>`. `ArcProperty` carries its ID, predicate IRI, value, and ID-keyed annotations.
- Object annotations become `Map<AnnotationId, ArcAnnotation>`; relation annotations follow the same rule.
- `ArcIR.Relations` becomes `Map<RelationId, ArcRelation>`, and `ArcRelation.Id` is required rather than optional.
- Repeated independently curatable values are separate property assertions. `ArcValue.List` is retained only for an ordered value that is deliberately curated atomically.

F1 mints deterministic IDs from the source artifact identity, source selector, mapping/rule ID, and assertion role. IDs are never derived from the current assertion value, so a value edit cannot rename its slot. Curation-created assertions use opaque URI-shaped IDs. Existing IDs survive unchanged across later revisions unless an explicit identity-changing activity records their replacement.

Replace silent overwrite behavior with explicit operations:

- `add` fails on an incompatible duplicate ID.
- `upsert` is available only where replacement is intentional and returns the replaced value.
- `merge` reports conflicts rather than selecting a winner silently.
- Validation detects missing endpoints, duplicate semantic slots where forbidden, invalid IRIs/IDs, and selectors that do not resolve.

### Migration

- Convert the current graph builders and all eight INSDC converters to the new maps and required IDs in one breaking change.
- Do not retain aliases or obsolete overloads for the proof-of-concept shapes.
- Add compile-time and golden-fixture tests before deleting the old core types from `BioFSharp.INSDC.ArcIR`.

### Phase acceptance

- The target-neutral package builds and tests without an INSDC dependency.
- Every independently curatable graph element has a stable identity.
- Merging graphs cannot silently lose a property, annotation, or relation.
- All eight current INSDC entity converters build against the extracted core.

## Phase 3 — Deterministic persistence and fragment addressing

### Canonical `.arcir.json`

Add a reversible, schema-versioned serializer and parser for this normalized root:

```json
{
  "formatVersion": "1.0",
  "graph": {
    "objects": {},
    "relations": {}
  }
}
```

- Commit a JSON Schema for each supported major format version.
- Serialize all addressable collections as objects keyed by stable IDs.
- Order keys deterministically, use invariant scalar formatting and UTF-8, and produce byte-identical output for the same graph.
- Reject unknown major versions; migrate known older versions explicitly before model decoding.
- Write atomically so interruption cannot leave a truncated canonical IR file.
- Treat GraphML, JSON-LD, and visualization data as derived views, never as the authoritative editable state.

Example physical locations are:

```text
#/graph/objects/<escaped-object-id>
#/graph/objects/<escaped-object-id>/properties/<escaped-assertion-id>
#/graph/relations/<escaped-relation-id>
```

### Typed locations and external references

Add neutral addressing types to the core library:

```fsharp
type ArtifactRevision =
    { Path: string
      Sha256: string
      Commit: string option }

type FragmentSelector =
    { ConformsTo: Iri
      Value: string }

type FragmentRef =
    { Artifact: ArtifactRevision
      Selector: FragmentSelector }

type ArcLocation =
    | Object of ArcId
    | TypeAssertion of ArcId * AssertionId
    | Property of ArcId * AssertionId
    | ObjectAnnotation of ArcId * AnnotationId
    | PropertyAnnotation of ArcId * AssertionId * AnnotationId
    | Relation of RelationId
    | RelationAnnotation of RelationId * AnnotationId
```

`ArcIRJson.selector` is the only component that converts an `ArcLocation` to an RFC 6901 URI-fragment JSON Pointer. F1, curation, F2, and UI code work with typed locations and must not hard-code the wire layout or escaping rules.

Use the same `FragmentRef` abstraction for source XML XPointer, RFC 7111 table fragments, IR JSON Pointer, SSSOM mapping-record identity, transformation records, and diagnostic reports. A fragment never floats across revisions: an activity records distinct input and output references even when their semantic identity is preserved.

`ArtifactRevision.Commit` is resolver metadata and may be absent from an artifact record committed in that same revision, avoiding a self-referential commit hash. Path plus SHA-256 digest is sufficient for identity; the enclosing Git commit or process resolver supplies the commit when known.

### Phase acceptance

- Semantic and byte-for-byte round trips pass for representative and adversarial graphs.
- Golden files demonstrate deterministic ordering and JSON Pointer escaping for `/`, `~`, Unicode, and URI-shaped IDs.
- Every generated `ArcLocation` resolves to exactly one fragment in the serialized document.
- Editing and reserializing one assertion produces a small localized Git diff.

## Phase 4 — SSSOM-backed semantic mappings

Create a separate `BioFSharp.ArcIR.SSSOM` package so SSSOM parsing and validation do not enlarge the core graph model.

### Boundary

SSSOM mapping sets contain reusable semantic claims such as:

- an INSDC schema/local property term to an ArcIR predicate or type;
- an INSDC controlled value to an ontology term;
- curated negative mapping knowledge where the SSSOM model supports it.

They do not contain XPath/XPointer selectors, parsing or normalization operations, object construction, identifier minting, record-specific values, or execution provenance. Those remain transformation rules and records.

### Format and identity

- Target the released SSSOM 1.0 specification and pin the normative schema/examples used for conformance.
- Preserve mapping predicates, justifications, creators, provenance, and extension metadata; never collapse a mapping to `Iri -> Iri`.
- Require a stable URI-shaped mapping-record ID in the ArcIR-facing API.
- Persist that ID as the declared SSSOM 1.0 extension column `ext_arc_record_id`. Accept the SSSOM 1.1 `record_id` spelling on import once encountered, mapping both to the same internal field.
- When importing a 1.0 mapping set without record IDs, create an ARC-owned canonical copy and mint opaque IDs. Never use row numbers or the subject/predicate/object tuple as identity.
- Reference a mapping by mapping-set artifact revision plus mapping-record ID, not by a mutable mapping-set name alone.
- Provide deterministic embedded-metadata TSV read/write and validation. Keep registry access, RDF/OWL conversion, and remote prefix resolution out of the first implementation.

All reusable structural and content mappings currently hard-coded or represented by the generated structural ontology move into versioned mapping sets. Extraction remains explicit typed converter logic; local source terms provide the stable SSSOM subject side.

### Phase acceptance

- Official positive examples and local negative fixtures cover quoting, multivalues, prefixes, extensions, missing mandatory fields, and deterministic round trips.
- Canonical output retains `ext_arc_record_id` across supported round trips.
- Differential conformance against a pinned `sssom-py` CLI runs in a separate FAKE target.
- An unmapped source term remains in the IR and emits a diagnostic without aborting F1.

## Phase 5 — Auditable F1 and unified diagnostics

### One result and diagnostic model

Replace stage-specific `F1Report`/`F2Diagnostic` concepts with:

```fsharp
type DiagnosticSeverity =
    | Info
    | Warning
    | Error

type Diagnostic =
    { Id: DiagnosticId
      Code: Iri
      Severity: DiagnosticSeverity
      Message: string
      Targets: FragmentRef list
      Related: FragmentRef list }

type DiagnosticReport =
    { Id: ArcId
      Diagnostics: Map<DiagnosticId, Diagnostic> }

type TransformationOperation =
    { Operation: Iri
      Input: ArcValue
      Output: ArcValue
      Parameters: Map<string, ArcValue> }

type SourceOutputBinding =
    { Sources: FragmentRef list
      Outputs: FragmentRef list
      Rule: Iri
      MappingRecords: FragmentRef list
      Operations: TransformationOperation list }

type FieldDisposition =
    | Emitted of output: FragmentRef list
    | IntentionallyIgnored of rule: Iri * reason: string
    | Unsupported of diagnostic: DiagnosticId
    | Failed of diagnostic: DiagnosticId

type TransformationRecord =
    { Id: ArcId
      Inputs: ArtifactRevision list
      Outputs: ArtifactRevision list
      Bindings: SourceOutputBinding list
      FieldDispositions: Map<FragmentRef, FieldDisposition> }

type TransformationResult<'output> =
    { Output: 'output
      Record: TransformationRecord
      Diagnostics: DiagnosticReport }
```

The producing ARC activity establishes whether a report came from F1, curation, validation, or F2; `Diagnostic` therefore has no stage field. Historical diagnostics are immutable. A curation activity may declare that it addresses diagnostic IDs, but it never changes their status in the old report.

At the API boundary a result bundles output, transformation record, and diagnostics for convenience. At rest they are separate generated artifacts connected by the activity.

### F1 transformation record and field accounting

- Complete explicit F1 mapping for all eight supported INSDC entities and supplementary paper/count metadata against the new core.
- Give every extraction/emission rule a stable ID.
- For every present source leaf from `xpathEntries`, record exactly one field-accounting outcome: emitted, intentionally ignored with a rule and reason, unsupported with a diagnostic, or failed with a diagnostic.
- Store source-to-output bindings separately from diagnostics. Each binding identifies source fragments, output fragments, the rule, mapping-set revision and mapping-record IDs used, and effectful operations.
- Record an operation only when it changed meaning or representation, such as trimming changed whitespace, parsing a date, splitting a value, or applying a semantic mapping. Mere selection and copying are represented by the binding, not padded into an operation log.
- Preserve source artifact and selector provenance on generated assertions without turning source selectors into graph nodes.

An F1 activity uses source artifact revisions, a transformation recipe/version, mapping-set revisions, and software identity. It generates the initial canonical ArcIR revision, a transformation record, and a diagnostic report.

### Phase acceptance

- Every leaf in each committed eight-entity fixture is accounted for.
- Tests resolve every source and output fragment in every transformation-record binding.
- Repeated F1 execution with identical artifacts, recipe, and mapping sets produces semantically identical IR and deterministic IDs.
- Missing mappings, lossy conversions, conflicts, and unsupported fields produce stable diagnostics while preserving usable source information.

## Phase 6 — Git-backed curation activities

Add a curation/process library that applies typed graph operations and emits ARC process records. The process graph, not the ArcIR file, is the authority for lineage, agents, software versions, used/generated artifacts, and activity relationships.

### State transitions

- A curation activity consumes the canonical IR at the parent revision and generates the same path with a new digest.
- The operation records input and output `FragmentRef` values and any diagnostics it addresses.
- IDs for unchanged assertions survive; replaced assertions receive explicit correspondence in the activity/transformation record.
- Validation runs before commit and generates its own report artifact when findings exist.
- Git supplies the human-readable diff and immutable revisions; the library does not generate numbered state files or require JSON Patch artifacts.

### Term correction and mapping promotion

A curator changing an instance term and promoting that decision for future ingests creates two linked activities:

1. **Instance curation** consumes the old IR revision and generates the curated IR revision.
2. **Mapping promotion** consumes the relevant source/output evidence and prior SSSOM revision, then generates a new SSSOM revision.

They may be committed in one user-visible Git commit but remain distinct process activities with separate used/generated artifacts. The commit contains one repeatable trailer per activity:

```text
ARC-Activity: <activity-id-1>
ARC-Activity: <activity-id-2>
```

The activity records reference generated paths and digests; commit association is resolved from the trailers after the commit exists, avoiding circular hashes. Promoting a mapping affects future F1 lineages and does not silently rerun F1 over the currently curated IR.

### Phase acceptance

- A fixture curation ARC demonstrates initial F1, an assertion correction, a two-activity correction/promotion commit, validation, and a later F2 run.
- Every used/generated artifact digest resolves at the associated Git revision.
- Reverting a commit restores the exact prior IR and process state.
- The process graph can answer which source fragment, rule, mapping record, curator, and activity produced any selected assertion.

## Phase 7 — Define the F2 compiler boundary

Define a target-neutral compiler contract, a target-profile contract, and test doubles; do not implement an ARC, RO-Crate, ISA, readiness-level, or other concrete target in this roadmap.

An F2 compiler:

- consumes an exact `ArtifactRevision` of canonical ArcIR plus an immutable target profile/recipe;
- validates profile preconditions without mutating the IR;
- generates one or more target artifacts, a source-to-output transformation record, and the common diagnostic report;
- binds every generated target fragment back to the IR fragments that informed it;
- is deterministic for identical inputs unless the profile explicitly declares a nondeterministic dependency.

F2 can run repeatedly for different profiles or after later curation commits. It never generates a new IR state merely because target validation found a problem; any resulting correction is a separate curation activity.

### Phase acceptance

- A test compiler proves the interface with multi-file output, warnings/errors, fragment bindings, and deterministic reruns.
- F1, curation, validation, and F2 reports deserialize through the same diagnostic schema.
- No target-specific types or dependencies enter `BioFSharp.ArcIR`.

## Phase 8 — Replace the visualization layer

Create a separate read-only React/TypeScript/Vite workbench under `tools/arcir-workbench/`, using pinned stable Sigma v3, Graphology, and React Sigma packages. It reads canonical `.arcir.json` plus optional transformation-record, diagnostic, SSSOM, and process-graph artifacts through a shared loader validated against the JSON schemas.

### Workbench behavior

- Search and filter by object kind, type, predicate, source artifact, mapping record, diagnostic severity/code, and activity/revision.
- Use stable object/relation/assertion IDs for selection and deep links.
- Show a detail inspector for properties, annotations, provenance, source/output fragment references, mappings, diagnostics, and process history.
- Provide revision and activity views that explain what changed and why; use Git/process data rather than inventing history from the current graph.
- Distinguish missing endpoints and invalid fragments visually instead of silently dropping them.
- Keep layouts deterministic where practical, move expensive layout work off the UI thread, and degrade gracefully for large graphs through filtering and progressive detail.
- Support keyboard navigation, accessible color/shape encodings, copyable selectors, and export of the current filtered view.

Remove the embedded `Html.fs` viewer after the workbench covers its smoke-test use cases. Retain and improve GraphML as a derived interoperability export: preserve stable node/relation IDs, full IRIs, types, annotations, provenance references, and missing-node placeholders without claiming reversible persistence.

### Phase acceptance

- Unit tests cover schema loading, graph projection, filtering, fragment resolution, and deterministic style assignment.
- Browser tests cover loading the representative fixture, searching, selecting assertions, viewing diagnostics/provenance, switching revisions, and exporting a filtered view.
- A large synthetic graph remains interactive within a documented performance budget.
- No workbench action mutates or commits the curation ARC in this phase.

## End-to-end completion criteria

- A real committed INSDC fixture set can be ingested once into canonical `.arcir.json`, inspected, curated through multiple Git revisions, and consumed by the test F2 compiler.
- Any independently curatable assertion can be selected in its exact artifact revision and traced to source fragments, rules, mappings, diagnostics, activities, and generated target fragments.
- IR persistence is deterministic, reversible, schema-versioned, and independent of INSDC or any F2 target.
- Diagnostics are external immutable activity outputs, while the canonical IR contains only graph state.
- The read-only workbench replaces the barebones HTML visualization and accurately exposes the same provenance and addressing model used by the libraries.

## Explicit non-goals for this roadmap

- A compatibility layer for the proof-of-concept ArcIR API or serializer-default shapes.
- A second automatic F1 pass over an already curated lineage.
- Patch-chain persistence, numbered IR snapshots, or diagnostics embedded in the IR.
- A concrete production F2 target.
- A browser-based curation editor or Git writer.
- Requiring every local INSDC term to have an external ontology mapping.
- Treating GraphML, JSON-LD, the workbench projection, or SSSOM as the ArcIR persistence format.

## Execution order and release discipline

- Deliver phases in order. A later phase may prototype against an earlier branch, but it does not merge until the preceding phase's acceptance criteria pass.
- Keep model/wire-format changes and generated migrations in explicit release notes. Increment the ArcIR format major version for breaking wire changes and package major versions for breaking public API changes.
- Use FAKE targets as the solution-wide source of truth; CI remains a thin invoker.
- Each phase ends with updated schemas, fixtures, XML documentation, package READMEs, release notes, and an end-to-end example appropriate to that phase.
